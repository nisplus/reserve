# 当日空き状況サイト 設計書

当日の各社の空き状況を、来場者が見られるようにするための設計です。
開催情報（`events` / `event_sessions`）は既存の予約システムのものをそのまま使います。

**この設計のいちばんの制約は「運用中の予約システムに影響しないこと」**で、
以下の判断はすべてそこから導いています。

---

## 1. なにを作るのか

| | |
|---|---|
| 公開ページ | 当日の空き状況を一覧表示。認証なし。来場者が見る |
| 入力画面 | 事務局と会社担当者が空き状況を登録する。管理画面の中 |

### 前提として押さえておくこと

**当日券は紙で渡すため、システムは実際の残数を知りません。**
したがって `event_sessions.confirmed_seats`（予約システムが持つ確定席数）は、
当日の空き状況としては**正しくありません**。

> 例: 定員 20・予約 12 の回に、当日券を紙で 8 枚配った
> → システムは「残り 8 名」と言うが、実際は満席

この設計では、**予約システムの残数を当日空き状況として表示しません。**
表示するのは、人が入力した報告だけです。これは制約ではなく、
この機能が存在する理由そのものです。

---

## 2. リポジトリをどうするか（検討結果）

ご用意いただいた `slot_vacancy` を使うか、`reserve` の中に作るかの検討です。

### 選択肢

| | 方式 | 評価 |
|---|---|---|
| **A** | `reserve` に機能として追加 | **推奨** |
| B | `slot_vacancy` で新規に作り、同じ DB を読む | 認証を作り直す必要がある |
| C | `reserve` を fork して `slot_vacancy` にする | **非推奨**（後述） |

### データ面の影響は、どれを選んでも同じ

先に結論を言うと、**「予約システムに影響しない」という観点では A・B に差がありません。**

この機能が DB に対してすることは、次の 2 つだけだからです。

- **読む**: `events` / `event_sessions` / `companies`（SELECT のみ）
- **書く**: 新設する空き状況テーブル（INSERT のみ）

`bookings` にも `event_sessions.confirmed_seats` にも、予約トランザクションにも、
**一切触れません**。どちらのリポジトリに置いても、この性質は変わりません。

差が出るのは、**運用面**です。

### A を推奨する理由

**1. 認証と権限が、そのまま使えます**

「各社担当者も自社の空き状況を登録できる」——これは、すでにあるものです。

| 必要なもの | reserve の既存実装 |
|---|---|
| 会社担当者アカウント | `admin_users`（`role` + `company_id`） |
| 自社だけに絞る | `Authz::scopeCompanyId()` |
| 他社は 404 で隠す | `Authz::assertCompany()` |
| ログイン・ロックアウト・自動ログアウト | `Auth`（10回失敗で15分、30分/8時間） |
| CSRF | `Csrf` |

B で作る場合、これを**ゼロから作り直すか、同じ `admin_users` を読む別のログイン機構を書く**ことになります。
前者は 1〜2 日の追加、後者は**認証ロジックが 2 箇所に分かれる**という、
いちばん分かれてほしくない形の重複です。

**2. スキーマの所有者が 1 つに決まります**

新テーブルは `events` / `event_sessions` を外部キーで参照したい。
参照するなら同じ DB です。そのとき、

- 同じ DB のスキーマを 2 つのリポジトリのマイグレーションが変更する
- どちらの `migrate.php` を先に流すかが運用手順に出てくる
- `reserve` 側がカラムを変えたとき、`slot_vacancy` が黙って壊れる

という問題が残ります。A なら「この DB のスキーマは `reserve` が持つ」で一貫します。

**3. 個人開発の維持コスト**

B は、config・デプロイ手順・cron・テスト・ドキュメントが**恒久的に 2 系統**になります。
3 日程度の機能に対して、この負担は見合わないと考えます。

### B の唯一にして最大の利点

**当日、予約システムに一切触れずに空き状況サイトだけを直せること。**

A の場合、当日に表示を微修正したくなると `git pull` が予約システムのファイルも含みます
（内容が変わっていなければ中身は同一ですが、デプロイ操作そのものは発生します）。

**次のいずれかに当てはまるなら、B を選ぶ価値があります。**

- 当日、空き状況サイトを**別の人**が運用・修正する
- **別のサーバー**に置きたい（アクセス集中を予約システムから切り離したい）
- 予約システムは当日すでに停止しており、触りたくない

**そうでなければ A をおすすめします。**

### C を推奨しない理由

`reserve` を fork すると、**予約システムのコードが 2 本**になります。
予約側に修正が入るたび、どちらに入れたか・取り込んだかを管理し続けることになり、
得るものに対して代償が大きすぎます。

`slot_vacancy` を使うなら、**fork ではなく空のリポジトリから**作ってください。

### 以下の設計は A（`reserve` 内）を前提に書きます

B を選ばれた場合に変わるのは次の 3 点だけで、**データ設計は同じです**。

1. 認証を `slot_vacancy` 側に実装する（または入力画面だけ `reserve` に残す）
2. マイグレーションをどちらが持つか決める
3. DB 接続ユーザーを分け、新テーブル以外は SELECT のみの権限にする（**B ならこれは積極的にやる価値があります**）

## 3. データ設計

### 新テーブル（1つだけ）

```sql
-- db/migrations/012_vacancy.sql
CREATE TABLE vacancy_reports (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  event_id    INT UNSIGNED NOT NULL,
  session_id  INT UNSIGNED NULL,
  level       VARCHAR(8)  NOT NULL,
  remaining   SMALLINT UNSIGNED NULL,
  note        VARCHAR(200) NULL,
  reported_at DATETIME NOT NULL,
  reported_by VARCHAR(100) NOT NULL,
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

  CONSTRAINT fk_vacancy_event   FOREIGN KEY (event_id)   REFERENCES events(id)         ON DELETE CASCADE,
  CONSTRAINT fk_vacancy_session FOREIGN KEY (session_id) REFERENCES event_sessions(id) ON DELETE CASCADE,
  KEY idx_vacancy_latest (event_id, session_id, id),
  KEY idx_vacancy_reported (reported_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**既存テーブルは 1 列も変更しません。** `CREATE TABLE` だけのマイグレーションなので、
本番に適用しても予約システムの挙動は変わりません（010 と同じ考え方です）。

### なぜ履歴を積む形（追記のみ）にするか

`UPDATE` で現在値を上書きするのではなく、**報告のたびに 1 行足します**。

- **当日は伝言ゲームです。** チャットで聞いた内容を事務局が入力するので、
  「誰が・いつ・何と言ったか」が残らないと、食い違ったときに確認できません
- 「10:35 現在」を出すには、どのみち報告時刻が要ります
- **既存テーブルへの書き込みが構造的にゼロ**になります。追記しかしないので、
  不具合があっても過去のデータを壊しません

現在値は「`(event_id, session_id)` ごとの最新 1 件」で求めます
（`GROUP BY` + `MAX(id)` + join back。一斉送信の宛先抽出と同じ形です）。

### `session_id` の NULL が意味すること

| | 意味 |
|---|---|
| `session_id IS NULL` | **その体験の「現在の」空き状況**。開催回を区切らずに随時受け付けている場合 |
| `session_id` あり | **その開催回の**空き状況 |

ご要望の「開催回が設定されていない場合は現在の空き状況を登録する」に対応します。
入力画面では開催回の選択を**任意**にし、未選択なら「現在の状況」として記録します。

> 現在のデータは全 57 イベントが開催回を 5〜10 個持っていますが、
> 当日に 570 枠すべてをチャットで更新するのは現実的ではありません。
> **運用上は「現在の状況」（`session_id` なし）が主役**になる想定です。
> 開催回の指定は、「14:00 の回だけ満席」のような場合に使います。

### 空き状況の表し方

| `level` | 記号 | 表示 |
|---|---|---|
| `open` | ◎ | 今すぐ参加できます |
| `ample` | ◯ | 残席にゆとりがあります |
| `few` | △ | 残数わずか |
| `none` | ✕ | 残数なし |

- **記号は必須**です。公開ページのすべての行に記号が出るようにするためです
- **整理券残数（`remaining`）は任意**です。入っていれば「△ 残数わずか（残り 12 枚）」と併記します
- **残数に 0 を入れたときは、記号を自動的に ✕ にします**（入力の手間と、言っていることの矛盾を防ぐため）

`level` は列挙型ではなく `VARCHAR` にします。
MariaDB 11.8 が `CHECK` 制約を受け付けないため、値の妥当性は PHP 側
（`App\Domain\VacancyLevel`）で担保する——という既存の方針に合わせます。

## 4. 公開ページ

### URL

```
/vacancy            当日（既定）
/vacancy?date=      日付指定（前日準備・翌日の振り返り用）
```

### 表示

```
当日の空き状況                              10:35 現在

── 東エリア ─────────────────────────
  株式会社みらい工機
    工場見学ツアー            ◎ 今すぐ参加できます        10:32 現在
    組立体験                  △ 残数わずか（残り 6 枚）    10:28 現在

  となり電機株式会社
    製品体験ワークショップ    ✕ 残数なし                  10:15 現在
    技術説明会                — 未報告
```

- **会社ごと**にまとめ、エリア順・表示順（`companies.sort_order`, `events.sort_order`）で並べます
- 各行に**その報告の時刻**を出します。全体の「◯時◯分現在」はページの生成時刻です
- **未報告は「—」**と明示します。空欄にすると「報告がない」のか「空きがない」のか区別できません
- 一定時間（既定 90 分）更新がない行には「**情報が古い可能性があります**」を添えます
  当日いちばん危ないのは、更新が止まった企業の古い ◎ を見て来場者が向かうことです
- 60 秒ごとに自動更新（`<meta http-equiv="refresh">`）。JavaScript に依存しません

### 表示する対象

その日に開催回がある、**公開中の会社・公開中の体験**のみ。
`booking_required = 0`（予約不要）の体験も対象です——当日券の列ができるのはむしろこちらです。

### 表示しないもの

- **予約システムの残席数**（`capacity - confirmed_seats`）。冒頭に書いた理由により、当日は誤情報になります
- 予約者の個人情報（そもそも読みません）

## 5. 入力画面

### URL と権限

```
GET  /admin/vacancy          一覧と入力（事務局＝全社／会社担当者＝自社のみ）
POST /admin/vacancy          報告を 1 件追加
```

権限は既存の `Authz::scopeCompanyId()` に委ねます。
会社担当者には自社の体験しか出ず、他社の `event_id` を直接 POST しても 404 です
（`Authz::assertCompany()`。既存の作法どおり、403 ではなく 404）。

### 画面

当日はスピードが命なので、**1 画面・1 クリックで更新できる**形にします。

```
当日の空き状況の登録                              [日付: 2026-10-10]

 体験内容                    現在          最終更新    変更
─────────────────────────────────────────────────────
 工場見学ツアー              ◎ 今すぐ…    10:32      [◎][◯][△][✕]  残数[   ]
 組立体験                    △ 残数わずか  10:28      [◎][◯][△][✕]  残数[ 6 ]
 製品体験ワークショップ      — 未報告      —          [◎][◯][△][✕]  残数[   ]
```

- 記号のボタンを押すと、その場で 1 件記録されます（残数は任意入力）
- **確認ポップアップは出しません。** 当日に何度も押すものなので、
  毎回確認を求めると押されなくなります。取り消しも「正しい値を押し直す」で足ります
  （追記式なので、押し間違えても履歴に残るだけで、最新が正しければ正しく表示されます）
- 開催回を指定したい場合のみ、行を開いて回を選びます
- 直近の報告履歴（誰が・いつ・何を）を下に表示します

## 6. 予約システムに影響しないことの担保

| | |
|---|---|
| 既存テーブルへの書き込み | **なし**（`SELECT` のみ） |
| マイグレーション | `CREATE TABLE` 1 つ。既存テーブルは無変更 |
| `BookingService` / `CancellationService` / `WaitlistService` | **変更なし** |
| 既存ルート | 変更なし。`/vacancy` と `/admin/vacancy` を追加するのみ |
| 既存テンプレート | 変更なし（管理メニューに 1 行追加のみ） |
| 予約の停止・再開 | 空き状況の入力・表示とは独立（受付停止中でも入力できます） |
| ロールバック | テーブルを残したままルートを外せば、表示も入力も消えます |

テストは `tests/test_vacancy.php` を新規に追加し、既存 23 本には触れません。
検証項目は、最新 1 件の取り出し、会社スコープ（他社の体験に報告できないこと）、
開催回あり／なしの両方、残数 0 のときの記号自動補正、未報告の表示。

## 8. 決めていただきたいこと

1. **リポジトリ** — A（`reserve` 内。推奨）か B（`slot_vacancy`）か
2. **入力の主役** — 「現在の状況」（開催回なし）を既定にしてよいか
3. **整理券残数** — 記号と併記でよいか、それとも「数字か記号のどちらか一方」にするか
4. **古い情報の警告** — 90 分で「古い可能性」を出す、という閾値でよいか
